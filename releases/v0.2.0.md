# TotalRecall v0.2.0 — Single Database Backend

## What Changed

### Unified Database (BREAKING)

**Before:** Two separate SQLite files (`memory_log.db` + `total_recall.db`) in the same directory.
**After:** Single `totalrecall.db` containing all tables (`commands`, `chunks`, `memories`).

- Merged `MEMORY_LOG_SCHEMA` and `TOTAL_RECALL_SCHEMA` into single `SCHEMA`
- Replaced `init_memory_log()` + `init_total_recall()` with unified `init_db()`
- Consolidated `self.log_conn` + `self.recall_conn` into single `self.conn`
- All operations (ingest, chunk, compress, recall, status) now hit one database

### Migration

If you have existing data in v0.1.x format:

```bash
# Both databases are in ~/.totalrecall/
cd ~/.totalrecall/

# Merge into single DB
sqlite3 totalrecall.db ".attach 'memory_log.db' as old" \
  "INSERT INTO commands SELECT * FROM old.commands;" \
  "INSERT INTO chunks SELECT * FROM old.chunks;"

sqlite3 totalrecall.db ".attach 'total_recall.db' as old" \
  "INSERT INTO memories SELECT * FROM old.memories;"

# Verify and clean up
sqlite3 totalrecall.db "SELECT COUNT(*) FROM commands; SELECT COUNT(*) FROM memories;"
rm memory_log.db total_recall.db
```

### API Changes

- `TotalRecall.__init__()` — same signature, now creates one DB file
- All public methods (`ingest`, `assign_chunk`, `compress_chunk`, `compress_memories`, `recall`, `status`) — unchanged signatures and behavior
- `close()` — closes single connection instead of two

## Why

Two databases added unnecessary complexity with no real benefit. Both were in the same directory, used WAL mode, and accessed sequentially anyway. One database = simpler code, fewer file handles, easier backups.
